# Design

## Context

구현 대상은 `ddi_agent_proposal.md` 한 파일이다. 코드는 아직 없다. 결정 내용은 proposal.md(What Changes)와 specs/comparison-conditions에 있다. 이 문서에는 각 결정의 이유만 남긴다.

## Goals / Non-Goals

**Goals:**
- 문서만 읽어도 각 조건이 무엇을 받는지 모호하지 않게 한다
- 결정마다 이유를 한 줄씩 문서에 남겨, 논문 방법론을 쓸 때 다시 쓸 수 있게 한다

**Non-Goals:**
- 문서의 다른 장(용어집, 연구 개요, 데이터, 일정) 수정
- 질문 개수나 채점기 모델(8장 #1, #3) 결정

## Decisions

- **B에게도 환경 ②와 설명 파일을 준다.** 주지 않으면 B는 거의 모두 실행 단계에서 실패하거나 처음부터 해석할 수 없다. 그러면 가설의 핵심인 정확성(correctness) 비교가 불가능하다. 또 B와 C의 차이가 "환경 + ACI"가 되어 C가 이겨도 ACI 덕이라고 말할 수 없다.
  - 검토한 대안: B에게 환경 ①만 주기. 이 문제 때문에 채택하지 않음.
- **예측 서버는 C에게만 준다.** 환경 ②는 런타임이지만, 서버와 `ddi.predict()`는 ACI의 commands에 해당한다.
- **환경 ② 위치는 한 줄로 B와 C 모두에게 알려준다.** 이 한 줄은 ACI가 아니라 런타임에 대한 사실이다. 이 안내가 없으면 B는 10턴 안에 결과까지 도달하지 못할 위험이 크다.
- **B 실행 때는 `ddi` 패키지와 서버 코드를 컨테이너에서 뺀다.** import만 하지 않고 파일을 남겨 두면, B가 파일을 찾아서 쓸 수 있다.
- **`lookup_known`을 삭제한다.** 에이전트가 정답을 보면 성능 숫자가 실제보다 좋게 나온다. 또 채점 기준이 모델 예측이라, 모델이 틀린 쌍에서는 정답을 답한 C가 오히려 감점된다.
  - 검토한 대안: 조회 대상에서 테스트셋만 빼기. 삭제하는 쪽이 더 간단해서 채택하지 않음.
- **C′ ablation은 하지 않는다.** 실험을 간단하게 유지하기 위함. 논문의 주장은 "규칙과 도구를 함께 주면 더 정확하다"이고, 규칙과 도구의 효과를 따로 나누는 것은 목표가 아니다.
- **CSV에 `description`을 추가한다.** 관계 번호만으로는 약물 방향 오류(잘못된 해석 ②)를 채점할 수 없다.

## Risks / Trade-offs

- [심사에서 "규칙만 알려주면 되지 않냐"는 질문이 나올 수 있음] → 논문 한계 절에 C′을 하지 않았다고 한 줄 적는다
- [환경 ② 위치 안내 때문에 B의 실행 가능성(executability) 실패가 실제 사용 환경보다 적게 측정될 수 있음] → 문서에 이 안내가 있다고 명시해서, 실행 가능성 수치를 해석할 때 고려하게 한다
